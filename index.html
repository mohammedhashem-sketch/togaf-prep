📖 ADM Cycle + Phase Outputs Cheat Sheet

The ADM Cycle

Preliminary sets up the shop. Then A→H cycles around the center — Requirements Management — which touches every phase. Green arrows = normal flow. Iteration is expected; you may re-enter any phase.

Preliminary: Prep the org
A: Where are we going?
B–D: Design the target
E: Plan the work
F: Schedule & cost
G: Govern build
H: Manage change
RM: Feeds every phase

The Enterprise Continuum

Two parallel classifications: Architecture Continuum (the specs) and Solutions Continuum (the implementations). Both run generic → specific in the same order: Foundation → Common Systems → Industry → Organization-Specific. Architecture guides Solutions; Solutions inform Architecture.

Architecture Continuum (specs)
  • Foundation — TOGAF TRM, base generic services (e.g., OS abstractions, network protocols)
  • Common Systems — reusable across industries (e.g., generic security architecture, generic ERP model)
  • Industry — sector-specific (e.g., ARTS for retail, ACORD for insurance, TMForum for telco)
  • Organization-Specific — your enterprise's tailored EA
Solutions Continuum (implementations)
  • Foundation Solutions — OS, RDBMS, TCP/IP, HTTP
  • Common Systems Solutions — generic SAP, generic Salesforce, generic ServiceNow
  • Industry Solutions — SAP for Retail, Epic EMR, Guidewire for insurance
  • Organization-Specific Solutions — your customized SAP tenant, your custom apps

The Architecture Repository

The Architecture Repository is the storage layer for everything your EA function produces and consumes. Six primary components (with two more in TOGAF 10). The Enterprise Continuum is a view of the Repository — not a separate thing.

Metamodel: what artifacts exist
Capability: who + how
Landscape: the architecture itself
SIB: mandatory standards
Reference Library: reusable material
Governance Log: compliance history
Requirements Repo: cross-project reqs
Solutions Landscape: ABBs/SBBs in use
Common exam traps:
  • The Enterprise Continuum is a virtual view / classification of the Repository — NOT a physical database and NOT a separate store.
  • Architecture Landscape has THREE abstraction levels: Strategic → Segment → Capability (long-term → specific).
  • The SIB holds mandatory standards; the Reference Library holds reusable templates/patterns — different roles.
  • The Governance Log is where compliance reviews and architecture contracts are recorded for audit.

Complete Phase Outputs (Cheat Sheet)

Every phase's outputs, grouped as Deliverables (contractual documents), Artifacts (catalogs · matrices · diagrams), and Building Blocks (ABBs).

Preliminary Phase

Purpose: prepare the organization to do EA — scope, principles, capability, governance.
Deliverables: Organizational Model for EA · Tailored Architecture Framework · Initial Architecture Repository · Restatement of Business Principles/Goals/Drivers · Architecture Principles · Governance Framework · Request for Architecture Work (input to Phase A)

Phase A — Architecture Vision

Purpose: high-level vision of the target and get stakeholder buy-in.
Deliverables: Statement of Architecture Work (signed) · Architecture Vision · Communications Plan · Refined Architecture Principles · Business Scenarios · Capability Assessment · Tailored Architecture Framework · Draft Architecture Definition Document (ADD) · Draft Architecture Requirements Specification · Stakeholder Map

Phase B — Business Architecture

Purpose: design the Baseline & Target Business Architecture.
Deliverables: Baseline & Target Business Architecture · Business Architecture components of the Architecture Roadmap · updates to ADD, Requirements Spec
Artifacts (Catalogs): Organization/Actor · Driver/Goal/Objective · Role · Business Service/Function · Location · Process/Event/Control/Product · Contract/Measure
Artifacts (Matrices): Business Interaction · Actor/Role
Artifacts (Diagrams): Business Footprint · Business Service/Information · Functional Decomposition · Business Use-Case · Organization Decomposition · Product Lifecycle · Goal/Objective/Service · Business Capability Map · Value Chain / Value Stream

Phase C — Data Architecture

Purpose: define types & sources of data needed to support the business.
Deliverables: Baseline & Target Data Architecture · Data Architecture components of Roadmap
Catalogs: Data Entity/Data Component
Matrices: Data Entity/Business Function · Application/Data
Diagrams: Conceptual Data · Logical Data · Data Dissemination · Data Security · Data Migration · Data Lifecycle · Class

Phase C — Application Architecture

Purpose: define the applications needed to process data and support the business.
Deliverables: Baseline & Target Application Architecture · Application Architecture components of Roadmap
Catalogs: Application Portfolio · Interface
Matrices: Application/Organization · Role/Application · Application/Function · Application Interaction
Diagrams: Application Communication · Application & User Location · Application Use-Case · Enterprise Manageability · Process/Application Realization · Software Engineering · Application Migration · Software Distribution

Phase D — Technology Architecture

Purpose: define the technology capabilities and platforms.
Deliverables: Baseline & Target Technology Architecture · Technology components of Roadmap
Catalogs: Technology Standards · Technology Portfolio
Matrices: Application/Technology
Diagrams: Environments & Locations · Platform Decomposition · Processing · Networked Computing/Hardware · Communications Engineering

Phase E — Opportunities and Solutions

Purpose: identify projects, work packages, Transition Architectures. Strategy, not detailed plan.
Deliverables: Consolidated & Validated Architecture Roadmap · Transition Architectures (if needed) · INITIAL Implementation & Migration Plan · Implementation Factor Assessment & Deduction Matrix · Consolidated Gaps, Solutions & Dependencies Matrix · Business Value Assessment · Capability Assessment

Phase F — Migration Planning

Purpose: DETAILED implementation & migration plan — timed, costed, project-managed.
Deliverables: DETAILED Implementation & Migration Plan (timed & costed) · Finalized ADD · Finalized Requirements Spec · Finalized Architecture Roadmap · Finalized Transition Architectures · Implementation Governance Model
Trap: Phase E = INITIAL plan (strategy). Phase F = DETAILED plan (schedule + cost).

Phase G — Implementation Governance

Purpose: architectural oversight of implementation; ensure conformance.
Deliverables: Architecture Contracts (with implementation partners) · Compliance Assessments · Change Requests · Architecture-compliant solutions deployed · populated Architecture Repository · Implementation Governance Model (executed)

Phase H — Architecture Change Management

Purpose: manage changes to the architecture; decide when to re-enter ADM.
Deliverables: Architecture Updates · Changes to Architecture Framework/Principles · new Request for Architecture Work (if change triggers new cycle) · Statement of Architecture Work (updated) · Compliance Assessments (ongoing)
Change types: Simplification (no new capability) · Incremental (extends capability) · Re-architecting (new capability, restart ADM)

Requirements Management (Center — runs throughout)

Purpose: manage evolving requirements across every ADM phase.
Deliverables: Requirements Impact Assessment · updated Architecture Requirements Specification · populated Requirements Repository
Not a phase — it's the central hub. Every phase feeds requirements in and receives updates back.

🧠 Memorization Anchors

Phase → signature output (one per phase):
  • Preliminary → Request for Architecture Work + Governance Framework
  • A → Statement of Architecture Work + Architecture Vision + Draft ADD
  • B → Baseline & Target Business Architecture
  • C-Data → Baseline & Target Data Architecture
  • C-App → Baseline & Target Application Architecture
  • D → Baseline & Target Technology Architecture
  • E → Architecture Roadmap + Transition Architectures + INITIAL Migration Plan
  • F → DETAILED Migration Plan (timed & costed)
  • G → Architecture Contracts + Compliance Assessments
  • H → Change Requests (may trigger new ADM cycle)
  • RM → Requirements Impact Assessments + Requirements Repository
Draft vs Final ADD: Draft = end of Phase A. Finalized = end of Phase F.
Baseline first, then Target — order matters in every phase B/C/D.
Deliverable → Artifact → Building Block: Deliverable = contractual (signed). Artifact = granular work product (catalog/matrix/diagram). Building Block = reusable capability (ABB conceptual, SBB implementation).
